Let the Code Be Chaotic

A provocative position paper: the code an AI writes will never be the same twice. Stop trying to control it. Hold the behaviour, and let go of the rest

A provocative position paper: AI-generated code is chaotic, mostly harmlessly so. Teams should hold behaviour with tests and gates, not control the code.
Author

Stéphane Cuenat

Published

November 11, 2026

Position paper, November 2026. Provocative by intention. This paper takes a stance on purpose and states it more sharply than the evidence can yet prove: stop trying to control the code your AI writes. It is written to start an argument, not to close one. It borrows one idea from chaos theory, gathers what the last five years of research on AI coding have shown, says what the stance would mean for a team on Monday morning, and ends with tests that anyone can run against it. It continues Stop Reviewing Pull Requests. Figures 1 to 3 come from small simulations in sim.py, drawn by figs.py, with all numbers in results.json. Figure 4 is a schematic of my own.

Abstract. Ask an AI agent for the same feature twice and you get two different programs. Teams often react by trying to take control back: fixed seeds, line-by-line review of every diff, style rules, the demand that generation be reproducible. I argue that this reaction is aimed at the wrong target. Chaos theory has a name for systems whose path is unpredictable but whose behaviour is stable: systems with an attractor. AI-generated code is such a system when, and only when, the team has built the attractor: tests, checks and gates that pull the behaviour back to what was promised, every time the agent changes something. The paper splits the freedom of generated code into three zones: behaviour the checks hold, details nobody can observe, and behaviour that people can observe but nothing checks. The first is the team’s real product. The second can be left to the machine. The third is where almost every documented failure of AI coding sits, from insecure code to hallucinated packages. The provocation, stated plainly: hold the behaviour, let go of the code. I describe what this changes in a team’s roles, rituals and metrics, how security and the other “-ilities” fit, and five predictions that would show me wrong.

TipClaims
  1. The provocation. Stop trying to control the code an AI writes. Its unpredictability is real, and mostly harmless.
  2. Where stability comes from. Not from deterministic generation or careful reading, but from fast checks that pull behaviour back to the promise: an attractor.
  3. Three zones. Behaviour that checks hold; details nobody can observe; behaviour people can observe that nothing checks. Only the third is dangerous.
  4. The evidence. The documented failures of AI coding since 2021 sit almost entirely in the third zone, not in the code being different.
  5. For a team. Own the promise, not the text: write and review the checks, put a person only where harm cannot be undone, and measure how well the checks hold, not how many lines were read.
  6. Security is not an exception. It is the most important part of the third zone, and it moves into the first through checks, sandboxes and gates.

1. Introduction: the provocation

This paper is provocative by intention. I hold a view that most engineering teams would reject today, and I state it as sharply as I can so that it can be argued with:

Stop trying to control the code your AI writes. Control what it does.

Since 2023, more and more code is written by machines. The machines are not repeatable. The same request returns different programs; a sentence changed in the prompt, a different file opened in the context, and the agent takes another road and keeps building on it. This is measured, not anecdotal. Sending the same coding task to ChatGPT several times often returns programs that behave differently on the tests, and setting the temperature to zero reduces this without removing it (Ouyang et al. 2023). Even “deterministic” settings are not deterministic in practice: the output of a served model can depend on how many other requests happen to share its batch on the server (He and Thinking Machines Lab 2025).

For anyone trained to treat code as the thing a team owns and understands line by line, this feels like losing hold of the system. The natural response is to take hold again: review every diff, pin every seed, enforce every convention, ask the agent to explain each line. In Stop Reviewing Pull Requests I argued, with a cost model, that per-change approval no longer pays for itself. The objection I heard most was a single word: chaos. This paper takes the word literally.

2. What the last five years have shown

The research on AI coding since 2021 is large, and much of it is sobering. Read with one question in mind, where do things go wrong?, it tells a consistent story.

The field already measures behaviour, not code. When OpenAI introduced Codex and the HumanEval benchmark, it judged generated programs by whether they pass unit tests (pass@k), not by how close they are to a reference solution, because textual similarity says little about correctness (Chen et al. 2021). SWE-bench, the benchmark that most agent progress since 2024 is reported against, does the same with real GitHub issues: a patch counts if the repository’s tests pass after it is applied, whatever the code looks like (Jimenez et al. 2024). The research community quietly accepted, years ago, that two very different programs can both be right.

Passing weak tests is not being right. When Liu and colleagues added many more tests to HumanEval, a large share of programs that had “passed” turned out to be wrong: pass rates fell by up to 19 to 29% across 26 models (Liu et al. 2023). Nothing about the code changed. What changed was how much of the behaviour was checked.

Security failures live in behaviour nobody checked. About 40% of the programs Copilot wrote in security-relevant scenarios contained a known weakness (Pearce et al. 2022). In a controlled study, people with an AI assistant wrote less secure code than people without, and were more confident that it was secure (Perry et al. 2023). Code-generating models also invent dependencies: across 16 models and 576,000 samples, at least 5.2% of the packages suggested by commercial models and 21.7% of those suggested by open models did not exist, which attackers can register in their place (Spracklen et al. 2025).

Speed and stability are not yet won. In a controlled task, developers with Copilot finished 55.8% faster (Peng et al. 2023). In a randomized trial on large, mature open-source projects in early 2025, experienced developers were 19% slower with AI tools, while believing they had been faster (Becker et al. 2025). The DORA 2024 report associated more AI adoption with slightly lower delivery throughput and a 7.2% drop in delivery stability, and pointed at larger changes as the likely cause (DORA 2024). GitClear’s analysis of 211 million changed lines found copy-pasted code rising and refactoring falling, to the point where, in 2024, more lines were pasted than moved (GitClear 2025).

And the checks themselves can be generated. Meta’s TestGen-LLM used language models to extend existing unit tests, kept only the tests that built, passed reliably and raised coverage, and saw 73% of its proposals accepted by engineers for production (Alshahwan et al. 2024).

Put together, these results say something precise. The problems are real, but almost none of them is the code being different from what a human would have written. They are behaviour nobody checked (insecure patterns, missed edge cases, invented packages), feedback that came too late (large changes, slow review), and mass that nobody removed (duplicated code). Each of these is a failure of the attractor, not of control over the path.

3. A picture borrowed from chaos theory

In the early 1960s, Edward Lorenz restarted a simple weather model from numbers rounded to three decimals and watched the new forecast drift away from the old one until they had nothing in common. In 1963 he published the three-variable version that made the effect famous (Lorenz 1963). The lesson people remember is that the weather cannot be predicted for long. The lesson that matters here is the other half: all those unpredictable runs live on the same shape, the attractor, and the climate of the model, its averages and ranges, is perfectly stable (Strogatz 2015). Figure 1 shows both halves.

Software engineers have used this idea before. Netflix’s chaos engineering injects failures into production on purpose, and judges the system not by what happens inside it but by whether a steady state, the rate at which customers can watch, holds (Basiri et al. 2016). Nobody at Netflix tries to predict which server will fail. They make sure the steady state survives whichever one does.

Applied to generated code, the picture has three zones (Figure 4 below):

  • Zone 1, held. Behaviour the checks verify: tests, types, contracts, scanners, budgets. Every time the agent changes something, the checks pull it back. This is the attractor.
  • Zone 2, free and harmless. Everything nobody can observe from outside: names, structure, the order of lines, which of five equivalent algorithms was chosen this time. Two programs that differ only here are, for every user, the same program.
  • Zone 3, free and dangerous. Behaviour someone can observe, and may rely on, that no check holds: a security property, a latency, an edge case, an undocumented habit of an API. It drifts with the code, invisibly to the tests and visibly to users.

The provocation follows directly. Effort spent controlling zone 2 buys almost no stability, because nothing anyone sees lives there. Effort spent moving zone 3 into zone 1 buys almost all of it.

NoteFor readers who like equations: the model in two lines

Write the code as a state x in a very large space, and the behaviour as a much smaller observation of it, y = \phi(x). Many programs share the same behaviour, so most directions of x change nothing in y: that is zone 2, the null space of \phi. The checks hold some directions of y (zone 1) and leave others free (zone 3). If the agent, as a generator, pushes behaviour away from the promise at a rate \lambda, and each check-and-fix cycle of length \Delta t removes a share \kappa of the error it sees, the checked behaviour stays put when

-\frac{\ln(1-\kappa)}{\Delta t} \;>\; \lambda .

In words: the loop must pull back faster than the generator pushes away, but only in the directions it checks. This is the condition under which two chaotic systems stay synchronised when one is fed part of the other’s state (Pecora and Carroll 1990), with the specification playing the leading system. Everything else may stay chaotic.

4. A toy experiment

To see the picture work, I simulated it. It is a toy, labelled as one. The “code” is 300 numbers. The “agent” is a random recurrent network chosen to be chaotic on purpose (Sompolinsky et al. 1988), so that the code wanders unpredictably. The “behaviour” is 30 numbers computed from the code. The “tests” check some of those 30 numbers and, after every step, fix 80% of whatever error they see. Nothing else is controlled: the tests touch one direction of the code in ten.

Two runs, almost identical at the start. In Figure 2, two runs start from code that differs by one part in a hundred million. The code soon becomes as different as two unrelated programs. The tested behaviour also moves a little, but stays in a band about a hundred times narrower. In a second pair where a third of the behaviour is left untested, that untested part follows the code, not the tests: it drifts as far as the code does.

Coverage and speed, not determinism. Figure 3a repeats the experiment ten times at each level of test coverage. Without tests, behaviour is far from the specification. With half of it covered, the error is still 78% of that. With full coverage, it falls to 2.7%, while the code of different runs stays between 66% and 99% as different as unrelated programs. Figure 3b varies how chaotic the agent is and how firmly the loop corrects. The seven curves for seven levels of chaos lie on top of each other: in this toy, how wild the agent is barely matters; how fast and how firmly the checks pull back is what matters.

The toy proves nothing about real codebases. It shows that the picture is coherent: a chaotic generator and a stable behaviour can live together, and what separates them is coverage and speed of feedback. That matches what the studies in Section 2 found from the other side.

5. What it means for a team

If the provocation is right, a team’s job changes in concrete ways. This is the part I most want argued with.

What the team owns. Not the text of the code. The team owns three things: the promise (the intent, written down, as argued in Intent Is the Source), the checks that hold the promise, and the gates where a person must decide because harm cannot be undone. Code is an output of these, like compiled binaries were an output of source code. A team that cannot regenerate a module from its promise and its checks does not really own it, however carefully it read the diff.

What to stop.

  • Reading every generated diff to “understand the system”. The diff is a path in zone 2. Understanding belongs to the promise and the checks (see Review the Intent, Not the Diff).
  • Demanding reproducible generation. Pinned seeds and zero temperature make the path repeatable, not the behaviour correct, and serving infrastructure breaks them anyway (He and Thinking Machines Lab 2025).
  • Style debates about generated code, unless something observable depends on the rule. Then it is a check, not a preference.
  • Asking “who wrote this line?” The useful question is “which check should have caught this, and why did it not?”

What to start.

  • Checks first. Before an agent writes a feature, someone writes, or asks the agent to write and then reviews, the checks that define it. Review effort moves from code to tests, where a person can judge whether the promise is right.
  • Measure the attractor. Coverage is a weak proxy; mutation testing, which plants small bugs and checks whether the tests notice, measures how firmly the checks hold (Petrović and Ivanković 2018). Property-based tests hold whole families of behaviour at once (Claessen and Hughes 2000). Generated tests are fine if they are filtered the way Meta filtered them: they must build, pass reliably and add coverage (Alshahwan et al. 2024).
  • Make the loop fast. The same checks, run inside the agent’s session after every change, hold far more than the same checks run in a nightly pipeline. Speed of feedback is a stability property, not a convenience.
  • Regeneration drills. Borrowing from chaos engineering: from time to time, regenerate a module from its promise and its checks, and compare the old and new versions on random inputs (differential testing (McKeeman 1998)). Where they disagree, you have found zone 3. This is the cheapest way I know to find what nobody checks.
  • Turn real use into checks. What users and client services actually call, and actually rely on, becomes contract tests. This is how a team keeps up with the fact that people come to depend on every observable behaviour (Winters et al. 2020).
  • Budget the mass. Code size, duplication and coupling are observable to whoever must run and maintain the system, so they get budgets and checks too. The GitClear data on duplication (GitClear 2025) is a zone 3 failure, and Work Has Mass explains why it matters.

Roles. Each service or module has an owner of its attractor: the person accountable for the promise, the checks and the gates, rather than for the code. Reviewers review intent and checks. Security and platform engineers own the shared checks every agent session runs (Section 6). Nobody is accountable for reading every line, because nobody can be.

Metrics. Lines reviewed and pull requests approved stop being signs of care. What a team tracks instead:

Table 1. What a team measures when it holds behaviour rather than code.
Metric What it tells you
Escaped defects, classified by zone Whether failures come from unchecked behaviour (zone 3) or from weak checks (zone 1)
Mutation score of the checks How firmly the attractor holds
Time from change to check result How fast the loop pulls back
Behaviour agreement between regenerations How much of zone 3 is left
Size, duplication and coupling trends Whether the code is gaining mass

A useful test of the whole idea: if you deleted a module today and regenerated it from its promise and its checks, would you ship the result without reading it? If not, the reason you would hesitate is the list of things your checks do not hold. That list is the team’s real backlog.

6. Security and the rest, in a nutshell

The first question I am always asked is: and security? Security is not an exception to the provocation. It is the most important part of zone 3, and the documented AI coding failures in Section 2 show what happens when it is left there. The answer is the same as for everything else: move it into zone 1 with checks, and put a person at a gate only where harm cannot be undone. Table 2 gives the short version.

Table 2. Security and other concerns, each moved from zone 3 into zone 1, or placed behind a gate.
Concern How it is held, without reading every line
Injection, unsafe APIs, known weaknesses (Pearce et al. 2022) Static analysis and security linters in every agent session; security tests per entry point; known-bad patterns as failing checks
Secrets Secret scanning before anything leaves the session; credentials never in the agent’s reach
Dependencies and supply chain (Spracklen et al. 2025) Allowlist of packages and registries; lockfiles; provenance checks; new dependencies behind a gate
Access control and privacy Authorisation tests for every endpoint; data-flow checks on personal data; policy as code
The agent itself Sandboxed sessions; never private data, untrusted input and a way out at once (the Rule of Two in The Context Is the Wire)
Irreversible actions A thin human gate at the point of no return: migrations that drop data, payments, deletions, releases (see Stop Reviewing Pull Requests)
Performance and cost Budgets on latency, memory and cost per request, checked like tests
Maintainability Budgets on size, duplication and coupling; architecture rules as tests
Accessibility, licences, compliance Automated accessibility checks, licence scanning, compliance rules as code; sampling by a person where automation is weak
What cannot be checked: taste, fairness, product sense Human judgement at the level of the promise, not the diff

Two things in the table matter more than the rows. First, every row is something a team should do whether or not it reads the code: human review missed these failures before AI too, and Perry and colleagues found that people working with an assistant became more confident, not more careful (Perry et al. 2023). Second, the last row is real. Some properties cannot be checked by a machine. The provocation does not ask anyone to stop judging them; it asks that the judgement be made where it has leverage, on the promise and at the gate, not spread thin across thousands of generated lines.

7. Predictions, and what would change my mind

A provocation is only useful if it can lose. Each prediction names the result that would refute it.

  • P1. Regeneration. Regenerate a well-tested feature twenty times. The code will differ widely; behaviour will agree on the checks and disagree, outside them, in proportion to what is unchecked. Refuted if similarity of the code predicts correct behaviour better than coverage and mutation score do.
  • P2. Where failures come from. Defects that reach users from AI-written code will be mostly zone 3 (unchecked behaviour) or weak zone 1 (checks that do not hold), not “strange-looking code”. Refuted if code that reviewers flag as unusual predicts escaped defects better than gaps in the checks.
  • P3. Determinism buys little. Making generation reproducible will reduce escaped defects far less than the same effort spent on checks. Refuted if it reduces them at least as much, for comparable cost.
  • P4. Fast loops win. The same checks, run inside the agent’s session instead of later in CI, will reduce defects and rework. Refuted if timing makes no measurable difference.
  • P5. Teams. Teams that move review effort from diffs to checks, and track the metrics in Table 1, will deliver at least as fast with no more incidents than teams that review every diff. Refuted if, in a stepped-wedge trial like the one proposed in Stop Reviewing Pull Requests, they have more incidents or slower recovery.

8. Objections, and why they do not overturn the provocation

“This is randomness, not chaos.” Language model sampling is random; Lorenz’s chaos is deterministic. The difference does not help the objection. The argument needs only that small differences in input grow into large differences in code, and that the code stays bounded. Generated code has both, at any temperature (Ouyang et al. 2023; He and Thinking Machines Lab 2025). I used a deterministic chaotic agent in the toy to make the stronger point: even perfect determinism would not give back the control people want.

“Untested behaviour is exactly where the danger is.” Yes. That is the thesis, not an objection to it. Reading diffs does not find zone 3 reliably either: it is behaviour, and it shows up when the code runs, not when it is read. The way to find it is to run the code differently (regeneration drills, differential tests, production traffic turned into checks), and the way to hold it is a check.

“With enough users, everything observable is depended on.” Hyrum’s law (Winters et al. 2020) makes zone 3 grow over time, so the provocation asks for more checks as a system ages. That is a cost, but it is the honest cost of owning a system with users, and it applies to hand-written code too. Line-by-line control does not tell you what users depend on; observing them does.

“People still have to read the code.” Sometimes, today: in an incident, in a security audit, in a domain with no good checks. Reading is still allowed. What the provocation drops is reading as the default form of control, applied to every change. Where people must read, the structure they read is observable to them, so it becomes a zone 1 property with its own budget.

“Different implementations share the same blind spots.” They do: independently written versions of a program tend to fail on the same hard inputs (Knight and Leveson 1986), and twenty regenerations from one model are less independent still. The provocation does not claim regeneration gives redundancy. It claims that the differences between regenerations are mostly harmless, and that the shared blind spots are, again, unchecked behaviour.

“The checks can be wrong.” A strong loop around a wrong test holds the wrong behaviour very stably; an attractor is not a truth. This is why human attention should move to the promise and the checks, where a wrong expectation can be seen, rather than to the code, where it is buried.

“The evidence is mixed.” It is: AI tools made developers faster in one study and slower in another (Peng et al. 2023; Becker et al. 2025), and DORA saw stability fall as adoption rose (DORA 2024). I read the mixed results as support. They are what one would expect from teams that adopted a chaotic generator without building the attractor: larger changes, slower feedback, more mass. The provocation predicts that teams who build it will see the gains without the instability. P5 is the test.

“It is a toy.” The simulation is. The thesis does not rest on it; it rests on Sections 2, 5 and 6, and it will stand or fall on P1 to P5.

9. Conclusion

Lorenz did not show that the weather cannot be known. He showed that the weather and the climate are different questions, and that the second can be answered when the first cannot. AI-generated code is weather. The behaviour a team promised is climate. Trying to predict and control every line an agent writes is forecasting gusts.

So the provocation, once more, and on purpose: stop trying to control the code your AI writes. Own the promise, build the checks that hold it, put a person where harm cannot be undone, and let the rest be chaotic. Most of the chaos was never where the risk was.
