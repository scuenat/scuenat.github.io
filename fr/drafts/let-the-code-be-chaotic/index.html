Laissez le code être chaotique

Un article de position provocateur : le code qu’écrit une IA ne sera jamais deux fois le même. Cessez de vouloir le contrôler. Tenez le comportement, lâchez le reste

Article de position, novembre 2026. Provocateur à dessein. Cet article prend parti volontairement et énonce sa thèse plus nettement que les preuves ne le permettent encore : cessez de vouloir contrôler le code qu’écrit votre IA. Il est écrit pour ouvrir un débat, pas pour le clore. Il emprunte une idée à la théorie du chaos, rassemble ce que cinq ans de recherche sur le codage par IA ont montré, dit ce que cette position changerait pour une équipe dès lundi matin, et se termine par des tests que chacun peut lui opposer. Il prolonge Arrêtez de relire les pull requests. Les figures 1 à 3 viennent de petites simulations dans sim.py, dessinées par figs.py, et tous les nombres sont dans results.json. La figure 4 est un schéma de moi. Les figures sont en anglais. Traduit automatiquement de l’anglais ; quelques erreurs sont possibles. Version originale.

Résumé. Demandez deux fois la même fonctionnalité à un agent d’IA et vous obtenez deux programmes différents. Les équipes réagissent souvent en reprenant le contrôle : graines fixées, relecture ligne à ligne de chaque diff, règles de style, exigence d’une génération reproductible. Je soutiens que cette réaction vise la mauvaise cible. La théorie du chaos a un nom pour les systèmes dont la trajectoire est imprévisible mais dont le comportement est stable : les systèmes à attracteur. Le code généré par l’IA est un tel système quand, et seulement quand, l’équipe a construit l’attracteur : des tests, des vérifications et des barrières qui ramènent le comportement à ce qui a été promis, chaque fois que l’agent modifie quelque chose. L’article partage la liberté du code généré en trois zones : le comportement que les vérifications tiennent, les détails que personne ne peut observer, et le comportement que l’on peut observer mais que rien ne vérifie. La première est le vrai produit de l’équipe. La deuxième peut être laissée à la machine. La troisième est celle où se trouvent presque tous les échecs documentés du codage par IA, du code non sécurisé aux paquets hallucinés. La provocation, dite simplement : tenez le comportement, lâchez le code. Je décris ce que cela change dans les rôles, les rituels et les indicateurs d’une équipe, comment la sécurité et les autres exigences s’y intègrent, et cinq prédictions qui pourraient me donner tort.

AstuceThèses
  1. La provocation. Cessez de vouloir contrôler le code qu’écrit une IA. Son imprévisibilité est réelle, et le plus souvent sans conséquence.
  2. D’où vient la stabilité. Ni d’une génération déterministe ni d’une lecture attentive, mais de vérifications rapides qui ramènent le comportement à la promesse : un attracteur.
  3. Trois zones. Le comportement que les vérifications tiennent ; les détails que personne ne peut observer ; le comportement observable que rien ne vérifie. Seule la troisième est dangereuse.
  4. Les faits. Les échecs documentés du codage par IA depuis 2021 se trouvent presque tous dans la troisième zone, pas dans le fait que le code soit différent.
  5. Pour une équipe. Possédez la promesse, pas le texte : écrivez et relisez les vérifications, placez une personne seulement là où le dommage est irréversible, et mesurez la tenue des vérifications, pas le nombre de lignes lues.
  6. La sécurité n’est pas une exception. C’est la part la plus importante de la troisième zone, et elle passe dans la première par des vérifications, des bacs à sable et des barrières.

1. Introduction : la provocation

Cet article est provocateur à dessein. Je défends une position que la plupart des équipes d’ingénierie rejetteraient aujourd’hui, et je l’énonce aussi nettement que possible pour qu’on puisse la discuter :

Cessez de vouloir contrôler le code qu’écrit votre IA. Contrôlez ce qu’il fait.

Depuis 2023, de plus en plus de code est écrit par des machines. Ces machines ne sont pas reproductibles. La même demande renvoie des programmes différents ; une phrase changée dans le prompt, un autre fichier ouvert dans le contexte, et l’agent prend une autre route et continue de bâtir dessus. C’est mesuré, pas anecdotique. Envoyer plusieurs fois la même tâche de programmation à ChatGPT renvoie souvent des programmes qui se comportent différemment face aux tests, et une température nulle réduit cet effet sans le supprimer (Ouyang et al. 2023). Même les réglages « déterministes » ne le sont pas en pratique : la sortie d’un modèle servi peut dépendre du nombre d’autres requêtes qui partagent son lot sur le serveur (He et Thinking Machines Lab 2025).

Pour qui a appris à considérer le code comme la chose qu’une équipe possède et comprend ligne à ligne, c’est comme perdre prise sur le système. La réponse naturelle est de reprendre prise : relire chaque diff, fixer chaque graine, imposer chaque convention, demander à l’agent d’expliquer chaque ligne. Dans Arrêtez de relire les pull requests, je soutenais, avec un modèle de coût, que l’approbation de chaque modification ne se justifie plus. L’objection que j’ai le plus entendue tenait en un mot : chaos. Cet article prend le mot au pied de la lettre.

2. Ce que cinq ans ont montré

La recherche sur le codage par IA depuis 2021 est abondante, et souvent dégrisante. Lue avec une seule question en tête, où les choses tournent-elles mal ?, elle raconte une histoire cohérente.

Le domaine mesure déjà le comportement, pas le code. Quand OpenAI a présenté Codex et le banc d’essai HumanEval, les programmes générés étaient jugés sur leur réussite aux tests unitaires (pass@k), pas sur leur ressemblance avec une solution de référence, parce que la similarité textuelle dit peu de chose de la justesse (Chen et al. 2021). SWE-bench, le banc d’essai sur lequel se mesure l’essentiel des progrès des agents depuis 2024, fait de même avec de vrais tickets GitHub : un correctif compte si les tests du dépôt passent après son application, quelle que soit l’allure du code (Jimenez et al. 2024). La communauté de recherche a admis sans bruit, il y a des années, que deux programmes très différents peuvent être justes tous les deux.

Réussir des tests faibles n’est pas être juste. Quand Liu et ses collègues ont ajouté beaucoup plus de tests à HumanEval, une large part des programmes qui « passaient » se sont révélés faux : les taux de réussite ont baissé de 19 à 29 % sur 26 modèles (Liu et al. 2023). Le code n’avait pas changé. Ce qui avait changé, c’était la part du comportement vérifiée.

Les failles de sécurité vivent dans le comportement que personne n’a vérifié. Environ 40 % des programmes écrits par Copilot dans des scénarios sensibles pour la sécurité contenaient une faiblesse connue (Pearce et al. 2022). Dans une étude contrôlée, les personnes aidées d’un assistant d’IA écrivaient du code moins sûr que les autres, et en étaient plus convaincues de sa sécurité (Perry et al. 2023). Les modèles qui génèrent du code inventent aussi des dépendances : sur 16 modèles et 576 000 échantillons, au moins 5,2 % des paquets proposés par les modèles commerciaux et 21,7 % de ceux proposés par les modèles ouverts n’existaient pas, et des attaquants peuvent les enregistrer à leur place (Spracklen et al. 2025).

Vitesse et stabilité ne sont pas encore acquises. Sur une tâche contrôlée, des développeurs équipés de Copilot ont terminé 55,8 % plus vite (Peng et al. 2023). Dans un essai randomisé sur de grands projets open source matures, début 2025, des développeurs expérimentés étaient 19 % plus lents avec des outils d’IA, tout en croyant avoir été plus rapides (Becker et al. 2025). Le rapport DORA 2024 a associé une adoption plus large de l’IA à un débit de livraison légèrement plus faible et à une baisse de 7,2 % de la stabilité des livraisons, en désignant les modifications plus volumineuses comme cause probable (DORA 2024). L’analyse de GitClear sur 211 millions de lignes modifiées a montré le code copié-collé en hausse et le remaniement en baisse, au point qu’en 2024 plus de lignes ont été collées que déplacées (GitClear 2025).

Et les vérifications elles-mêmes peuvent être générées. TestGen-LLM, chez Meta, a utilisé des modèles de langage pour étendre des tests unitaires existants, n’a gardé que les tests qui compilaient, passaient de façon fiable et augmentaient la couverture, et a vu 73 % de ses propositions acceptées par les ingénieurs pour la production (Alshahwan et al. 2024).

Mis ensemble, ces résultats disent quelque chose de précis. Les problèmes sont réels, mais presque aucun n’est le fait que le code diffère de ce qu’un humain aurait écrit. Ce sont du comportement que personne n’a vérifié (motifs non sécurisés, cas limites oubliés, paquets inventés), une rétroaction trop tardive (grosses modifications, relecture lente) et une masse que personne n’a retirée (code dupliqué). Chacun est un échec de l’attracteur, pas du contrôle de la trajectoire.

3. Une image empruntée à la théorie du chaos

Au début des années 1960, Edward Lorenz relança un modèle météorologique simple à partir de nombres arrondis à trois décimales, et vit la nouvelle prévision s’écarter de l’ancienne jusqu’à n’avoir plus rien de commun avec elle. En 1963, il publia la version à trois variables qui rendit l’effet célèbre (Lorenz 1963). La leçon que l’on retient est que la météo ne se prévoit pas longtemps. La leçon qui compte ici est l’autre moitié : toutes ces trajectoires imprévisibles vivent sur la même forme, l’attracteur, et le climat du modèle, ses moyennes et ses amplitudes, est parfaitement stable (Strogatz 2015). La figure 1 montre les deux moitiés.

Les ingénieurs logiciels ont déjà utilisé cette idée. L’ingénierie du chaos de Netflix injecte volontairement des pannes en production et juge le système non sur ce qui se passe à l’intérieur, mais sur le maintien d’un état stable, le rythme auquel les clients peuvent regarder (Basiri et al. 2016). Personne chez Netflix ne cherche à prévoir quel serveur tombera. On s’assure que l’état stable survit, quel qu’il soit.

Appliquée au code généré, l’image comporte trois zones (figure 4 plus bas) :

  • Zone 1, tenue. Le comportement que les vérifications contrôlent : tests, types, contrats, scanners, budgets. Chaque fois que l’agent modifie quelque chose, les vérifications le ramènent. C’est l’attracteur.
  • Zone 2, libre et sans danger. Tout ce que personne ne peut observer de l’extérieur : les noms, la structure, l’ordre des lignes, celui des cinq algorithmes équivalents qui a été choisi cette fois. Deux programmes qui ne diffèrent que là sont, pour tout utilisateur, le même programme.
  • Zone 3, libre et dangereuse. Le comportement que quelqu’un peut observer, et sur lequel il peut compter, mais qu’aucune vérification ne tient : une propriété de sécurité, une latence, un cas limite, une habitude non documentée d’une API. Il dérive avec le code, invisible pour les tests et visible pour les utilisateurs.

La provocation en découle directement. L’effort passé à contrôler la zone 2 n’achète presque aucune stabilité, puisque rien de ce que l’on voit n’y vit. L’effort passé à faire passer la zone 3 dans la zone 1 en achète presque toute.

NotePour qui aime les équations : le modèle en deux lignes

Écrivons le code comme un état x dans un très grand espace, et le comportement comme une observation bien plus petite de cet état, y = \phi(x). Beaucoup de programmes partagent le même comportement, si bien que la plupart des directions de x ne changent rien à y : c’est la zone 2, le noyau de \phi. Les vérifications tiennent certaines directions de y (zone 1) et en laissent d’autres libres (zone 3). Si l’agent, en tant que générateur, écarte le comportement de la promesse à un taux \lambda, et si chaque cycle de vérification et de correction, de durée \Delta t, supprime une part \kappa de l’erreur qu’il voit, le comportement vérifié reste en place quand

-\frac{\ln(1-\kappa)}{\Delta t} \;>\; \lambda .

En mots : la boucle doit ramener plus vite que le générateur n’écarte, mais seulement dans les directions qu’elle vérifie. C’est la condition sous laquelle deux systèmes chaotiques restent synchronisés quand l’un reçoit une partie de l’état de l’autre (Pecora et Carroll 1990), la spécification jouant le rôle du système pilote. Tout le reste peut rester chaotique.

4. Une expérience jouet

Pour voir l’image fonctionner, je l’ai simulée. C’est un jouet, présenté comme tel. Le « code » est fait de 300 nombres. L’« agent » est un réseau récurrent aléatoire choisi chaotique à dessein (Sompolinsky et al. 1988), pour que le code erre de façon imprévisible. Le « comportement » est fait de 30 nombres calculés à partir du code. Les « tests » vérifient une partie de ces 30 nombres et, après chaque étape, corrigent 80 % de l’erreur qu’ils voient. Rien d’autre n’est contrôlé : les tests touchent une direction du code sur dix.

Deux exécutions presque identiques au départ. Dans la figure 2, deux exécutions partent de codes qui diffèrent d’une part sur cent millions. Les codes deviennent vite aussi différents que deux programmes sans rapport. Le comportement testé bouge un peu aussi, mais reste dans une bande environ cent fois plus étroite. Dans une seconde paire où un tiers du comportement n’est pas testé, cette partie suit le code, pas les tests : elle dérive autant que le code.

La couverture et la vitesse, pas le déterminisme. La figure 3a répète l’expérience dix fois pour chaque niveau de couverture des tests. Sans tests, le comportement est loin de la spécification. Avec la moitié couverte, l’erreur est encore à 78 % de cette valeur. Avec une couverture complète, elle tombe à 2,7 %, tandis que les codes des différentes exécutions restent entre 66 % et 99 % aussi différents que des programmes sans rapport. La figure 3b fait varier le degré de chaos de l’agent et la fermeté de la correction. Les sept courbes, pour sept niveaux de chaos, se superposent : dans ce jouet, la turbulence de l’agent compte à peine ; ce qui compte, c’est la vitesse et la fermeté avec lesquelles les vérifications ramènent.

Le jouet ne prouve rien sur de vraies bases de code. Il montre que l’image est cohérente : un générateur chaotique et un comportement stable peuvent coexister, et ce qui les sépare, c’est la couverture et la vitesse de la rétroaction. Cela rejoint ce que les études de la section 2 ont trouvé par l’autre bout.

5. Ce que cela veut dire pour une équipe

Si la provocation est juste, le travail d’une équipe change de façon concrète. C’est la partie que je souhaite le plus voir discutée.

Ce que l’équipe possède. Pas le texte du code. L’équipe possède trois choses : la promesse (l’intention, écrite, comme le soutenait L’intention est la source), les vérifications qui tiennent la promesse, et les barrières où une personne doit décider parce que le dommage serait irréversible. Le code est un produit de ces trois éléments, comme les binaires compilés étaient un produit du code source. Une équipe incapable de régénérer un module à partir de sa promesse et de ses vérifications ne le possède pas vraiment, si attentivement qu’elle ait lu le diff.

Ce qu’il faut arrêter.

  • Lire chaque diff généré pour « comprendre le système ». Le diff est une trajectoire dans la zone 2. La compréhension appartient à la promesse et aux vérifications (voir Relire l’intention, pas le diff).
  • Exiger une génération reproductible. Des graines fixes et une température nulle rendent la trajectoire répétable, pas le comportement juste, et l’infrastructure de service les met de toute façon en défaut (He et Thinking Machines Lab 2025).
  • Les débats de style sur le code généré, sauf si quelque chose d’observable dépend de la règle. Alors c’est une vérification, pas une préférence.
  • Demander « qui a écrit cette ligne ? ». La question utile est : « quelle vérification aurait dû l’attraper, et pourquoi ne l’a-t-elle pas fait ? »

Ce qu’il faut commencer.

  • Les vérifications d’abord. Avant qu’un agent écrive une fonctionnalité, quelqu’un écrit, ou fait écrire par l’agent puis relit, les vérifications qui la définissent. L’effort de relecture passe du code aux tests, là où une personne peut juger si la promesse est la bonne.
  • Mesurer l’attracteur. La couverture est un indicateur faible ; les tests de mutation, qui plantent de petits bugs et vérifient que les tests s’en aperçoivent, mesurent la fermeté des vérifications (Petrović et Ivanković 2018). Les tests de propriétés tiennent des familles entières de comportements à la fois (Claessen et Hughes 2000). Les tests générés conviennent s’ils sont filtrés comme Meta l’a fait : ils doivent compiler, passer de façon fiable et ajouter de la couverture (Alshahwan et al. 2024).
  • Rendre la boucle rapide. Les mêmes vérifications, lancées dans la session de l’agent après chaque modification, tiennent bien plus que les mêmes vérifications lancées dans une chaîne nocturne. La vitesse de rétroaction est une propriété de stabilité, pas un confort.
  • Des exercices de régénération. Emprunté à l’ingénierie du chaos : de temps en temps, régénérer un module à partir de sa promesse et de ses vérifications, et comparer l’ancienne et la nouvelle version sur des entrées aléatoires (test différentiel (McKeeman 1998)). Là où elles divergent, vous avez trouvé la zone 3. C’est le moyen le moins cher que je connaisse de découvrir ce que personne ne vérifie.
  • Transformer l’usage réel en vérifications. Ce que les utilisateurs et les services clients appellent vraiment, et sur quoi ils comptent vraiment, devient des tests de contrat. C’est ainsi qu’une équipe suit le fait que les gens finissent par dépendre de chaque comportement observable (Winters et al. 2020).
  • Budgéter la masse. La taille du code, la duplication et le couplage sont observables pour qui doit exploiter et maintenir le système ; ils reçoivent donc eux aussi des budgets et des vérifications. Les données de GitClear sur la duplication (GitClear 2025) décrivent un échec de la zone 3, et Le travail a une masse explique pourquoi il compte.

Les rôles. Chaque service ou module a un responsable de son attracteur : la personne qui répond de la promesse, des vérifications et des barrières, plutôt que du code. Les relecteurs relisent l’intention et les vérifications. Les ingénieurs sécurité et plateforme possèdent les vérifications partagées que toute session d’agent exécute (section 6). Personne ne répond de la lecture de chaque ligne, parce que personne ne le peut.

Les indicateurs. Le nombre de lignes relues et de pull requests approuvées cesse d’être un signe de soin. Voici ce qu’une équipe suit à la place :

Un test utile de toute l’idée : si vous supprimiez un module aujourd’hui et le régénériez à partir de sa promesse et de ses vérifications, livreriez-vous le résultat sans le lire ? Sinon, la raison de votre hésitation est la liste de ce que vos vérifications ne tiennent pas. Cette liste est le vrai carnet de travail de l’équipe.

6. La sécurité et le reste, en bref

La première question qu’on me pose est toujours : et la sécurité ? La sécurité n’est pas une exception à la provocation. C’est la part la plus importante de la zone 3, et les échecs documentés du codage par IA de la section 2 montrent ce qui arrive quand on l’y laisse. La réponse est la même que pour tout le reste : la faire passer dans la zone 1 par des vérifications, et placer une personne à une barrière seulement là où le dommage serait irréversible. Le tableau 2 en donne la version courte.

Tableau 2. La sécurité et les autres exigences, chacune passée de la zone 3 à la zone 1, ou placée derrière une barrière.
Exigence Comment la tenir, sans lire chaque ligne
Injections, API dangereuses, faiblesses connues (Pearce et al. 2022) Analyse statique et linters de sécurité dans chaque session d’agent ; tests de sécurité par point d’entrée ; motifs dangereux connus en vérifications bloquantes
Secrets Détection des secrets avant que quoi que ce soit ne quitte la session ; identifiants jamais à portée de l’agent
Dépendances et chaîne d’approvisionnement (Spracklen et al. 2025) Liste autorisée de paquets et de registres ; fichiers de verrouillage ; contrôle de provenance ; nouvelles dépendances derrière une barrière
Contrôle d’accès et vie privée Tests d’autorisation pour chaque point d’accès ; contrôle des flux de données personnelles ; règles sous forme de code

Ce qui ne se vérifie pas : le goût, l’équité, le sens du produit Le jugement humain au niveau de la promesse, pas du diff

Deux choses comptent plus que les lignes du tableau. D’abord, chaque ligne est quelque chose qu’une équipe devrait faire qu’elle lise ou non le code : la relecture humaine manquait déjà ces failles avant l’IA, et Perry et ses collègues ont montré que les personnes aidées d’un assistant devenaient plus confiantes, pas plus prudentes (Perry et al. 2023). Ensuite, la dernière ligne est réelle. Certaines propriétés ne peuvent pas être vérifiées par une machine. La provocation ne demande à personne de cesser d’en juger ; elle demande que ce jugement s’exerce là où il a du poids, sur la promesse et à la barrière, et non dilué sur des milliers de lignes générées.

7. Prédictions, et ce qui me ferait changer d’avis

Une provocation n’est utile que si elle peut perdre. Chaque prédiction nomme le résultat qui la réfuterait.

  • P1. Régénération. Régénérez vingt fois une fonctionnalité bien testée. Le code variera beaucoup ; le comportement concordera sur les vérifications et divergera, en dehors d’elles, en proportion de ce qui n’est pas vérifié. Réfutée si la ressemblance des codes prédit mieux le bon comportement que la couverture et le score de mutation.
  • P2. D’où viennent les échecs. Les défauts du code écrit par l’IA qui atteignent les utilisateurs relèveront surtout de la zone 3 (comportement non vérifié) ou d’une zone 1 faible (vérifications qui ne tiennent pas), pas d’un « code à l’allure étrange ». Réfutée si le code que les relecteurs jugent inhabituel prédit mieux les défauts échappés que les trous dans les vérifications.
  • P3. Le déterminisme rapporte peu. Rendre la génération reproductible réduira bien moins les défauts échappés que le même effort consacré aux vérifications. Réfutée si elle les réduit au moins autant, pour un coût comparable.
  • P4. Les boucles rapides gagnent. Les mêmes vérifications, lancées dans la session de l’agent plutôt que plus tard en intégration continue, réduiront les défauts et les reprises. Réfutée si le moment ne fait aucune différence mesurable.
  • P5. Les équipes. Les équipes qui font passer l’effort de relecture des diffs aux vérifications, et suivent les indicateurs du tableau 1, livreront au moins aussi vite, sans plus d’incidents, que les équipes qui relisent chaque diff. Réfutée si, dans un essai en escalier comme celui proposé dans Arrêtez de relire les pull requests, elles ont plus d’incidents ou se rétablissent plus lentement.

8. Objections, et pourquoi elles ne renversent pas la provocation

« C’est du hasard, pas du chaos. » L’échantillonnage d’un modèle de langage est aléatoire ; le chaos de Lorenz est déterministe. La différence ne sert pas l’objection. L’argument n’a besoin que de deux choses : de petites différences d’entrée deviennent de grandes différences de code, et le code reste borné. Le code généré a les deux, à toute température (Ouyang et al. 2023; He et Thinking Machines Lab 2025). J’ai utilisé un agent chaotique déterministe dans le jouet pour appuyer l’argument le plus fort : même un déterminisme parfait ne rendrait pas le contrôle que l’on souhaite.

« Le comportement non testé est justement là où est le danger. » Oui. C’est la thèse, pas une objection. Lire les diffs ne trouve pas non plus la zone 3 de façon fiable : c’est du comportement, et il se manifeste quand le code s’exécute, pas quand on le lit. Pour le trouver, il faut exécuter le code autrement (exercices de régénération, tests différentiels, trafic de production transformé en vérifications), et pour le tenir, il faut une vérification.

« Avec assez d’utilisateurs, tout ce qui est observable devient une dépendance. » La loi de Hyrum (Winters et al. 2020) fait grandir la zone 3 avec le temps, si bien que la provocation demande plus de vérifications à mesure qu’un système vieillit. C’est un coût, mais c’est le coût honnête de posséder un système qui a des utilisateurs, et il vaut aussi pour le code écrit à la main. Le contrôle ligne à ligne ne dit pas de quoi les utilisateurs dépendent ; les observer le dit.

« Il faut bien que des gens lisent le code. » Parfois, aujourd’hui : lors d’un incident, d’un audit de sécurité, dans un domaine sans bonnes vérifications. Lire reste permis. Ce que la provocation abandonne, c’est la lecture comme forme de contrôle par défaut, appliquée à chaque modification. Là où des gens doivent lire, la structure qu’ils lisent leur est observable, et devient donc une propriété de la zone 1, avec son propre budget.

« Des implémentations différentes partagent les mêmes angles morts. » C’est vrai : des versions écrites indépendamment d’un même programme échouent souvent sur les mêmes entrées difficiles (Knight et Leveson 1986), et vingt régénérations par un même modèle sont encore moins indépendantes. La provocation ne prétend pas que régénérer apporte de la redondance. Elle prétend que les différences entre régénérations sont surtout sans conséquence, et que les angles morts partagés sont, là encore, du comportement non vérifié.

« Les vérifications peuvent être fausses. » Une boucle forte autour d’un test faux tient le mauvais comportement de façon très stable ; un attracteur n’est pas une vérité. C’est pourquoi l’attention humaine doit se porter sur la promesse et les vérifications, où une attente fausse se voit, plutôt que sur le code, où elle est enfouie.

« Les résultats sont contradictoires. » Ils le sont : les outils d’IA ont rendu les développeurs plus rapides dans une étude et plus lents dans une autre (Peng et al. 2023; Becker et al. 2025), et DORA a vu la stabilité baisser quand l’adoption montait (DORA 2024). J’y vois un appui. C’est ce que l’on attendrait d’équipes qui ont adopté un générateur chaotique sans construire l’attracteur : modifications plus grosses, rétroaction plus lente, plus de masse. La provocation prédit que les équipes qui le construisent obtiendront les gains sans l’instabilité. P5 en est le test.

« Ce n’est qu’un jouet. » La simulation, oui. La thèse ne repose pas sur elle ; elle repose sur les sections 2, 5 et 6, et elle tiendra ou tombera sur P1 à P5.

9. Conclusion

Lorenz n’a pas montré que la météo est inconnaissable. Il a montré que la météo et le climat sont deux questions différentes, et que l’on peut répondre à la seconde quand on ne peut pas répondre à la première. Le code généré par l’IA est la météo. Le comportement promis par une équipe est le climat. Vouloir prévoir et contrôler chaque ligne qu’écrit un agent, c’est prévoir les rafales.

Alors, la provocation une dernière fois, et à dessein : cessez de vouloir contrôler le code qu’écrit votre IA. Possédez la promesse, construisez les vérifications qui la tiennent, placez une personne là où le dommage serait irréversible, et laissez le reste être chaotique. L’essentiel du chaos n’a jamais été là où était le risque.

À lire ensuite · Arrêtez de relire les pull requests Le versant économique du même argument : approuvez ce que vous ne pouvez pas défaire, surveillez tout le reste.
