A Grammar for Tools

MCP gave AI agents a dictionary. What it still lacks is a way to say how tools combine

essay
ai
agents
architecture
mcp
MCP lets every tool define itself, like words in a dictionary. Nothing in the protocol says how tools combine, so every agent rebuilds that knowledge on every run and forgets it at the end. I argue that the missing piece is a small grammar: rules over kinds of tools, and habits of specific tools, computed from schemas, declared by authors, observed in use and imposed by policy. OpenAPI, Arazzo and the semantic web tried parts of this before; what is new is a reader that can use it. I borrow the design principles from neural networks, without training one.
Author

Stéphane Cuenat

Published

October 30, 2026

Essay, October 2026. A follow-up to The Interface Is Data. The figures are my own, drawn with figs.py; all are schematics except Figure 3, which is plain counting. The roles, relations and JSON in Figures 2, 6 and 7 are a proposal of mine, not part of the MCP specification.

In short. The Model Context Protocol (MCP) gave AI agents a dictionary. Every tool defines itself: a name, a description, a schema for what it takes and what it returns. What MCP does not have is a grammar, a way to say how tools combine: which one must come first, which one feeds which, which ones are used together, which ones replace each other, and which ones must never meet in the same task. Today every agent rebuilds that grammar inside its context window, on every run, and forgets it at the end. With a few dozen tools that works. With thousands it does not, and the usual fix, searching tool descriptions, finds tools that look like the request, not tools that complete each other. I argue that the missing piece is a kind of object, the relation between tools, published as data. A useful grammar works at two levels: rules about kinds of tools (“anything that pays requires an approval”), which carry over to tools nobody has used yet, and habits of specific tools, learned from use. Relations can come from four sources (schemas, authors, use and policy), and each source has its own owner and its own level of trust. None of this is new in principle: OpenAPI has links between operations, its sister specification Arazzo (2024) writes down whole workflows, and the semantic web services of the 2000s described preconditions and effects. The older efforts stalled because writing a precise grammar cost too much and nothing could read an imprecise one. A language model can. The design principles come from neural networks (locality, sparse activation, plasticity, modularity and gating), but I no longer think we need to train a network to apply them.

TipKey takeaways
  • MCP is a dictionary. Each tool is defined on its own. The links between tools exist only inside one agent’s run.
  • The missing object is the relation. MCP has first-class tools, resources and prompts, and groups of tools are being proposed. It has no typed relation between tools, so nobody can publish, share, version or check one.
  • Resemblance is not complementarity. Searching descriptions finds tools like the request. A task needs tools that complete each other, and those rarely look alike. Tool-retrieval research since 2024 says the same.
  • The bottleneck is already visible. 2025 benchmarks with hundreds of MCP tools find that finding the right tool is the dominant failure, and that planning across steps and servers remains hard.
  • A grammar has two levels. Rules over roles (“pays requires approves”) hold for tools never seen before. Habits of named tools (“this payment tool is usually followed by that converter”) are sharp for known work and silent for new work.
  • Four sources, four owners. Edges are computed from schemas by any reader, declared by servers, observed by clients and imposed by the organisation’s gateway. Every edge should say where it came from.
  • This was tried before, in part. OpenAPI links, Arazzo workflows and semantic web services described how operations connect. Arazzo and agents.json write sentences (fixed workflows), not a grammar. The older efforts lacked a reader that could use a cheap, imperfect grammar. A language model is that reader.
  • Edges are local; names are not. Like links on the web, relations need no central map, but they do need stable names, which means a registry.
  • Borrow principles from neural networks, not the network. Locality, sparse activation, plasticity, modularity and gating describe how the grammar should behave. A learned router is an optimisation for later.

1. Points on a plane

Think of every MCP tool as a point. Its position is its meaning, what its description says it does. Two invoice tools sit close together; an invoice tool and a calendar tool sit far apart. A server publishes a handful of such points. A client connects to several servers and sees the union: a cloud of points with no lines between them (Model Context Protocol 2025c).

This is not a flaw. It is what made MCP so easy to adopt. A server does not need to know who else exists. Anyone can add a point, and every client can read it. That is the strength I described in The Interface Is Data: the interface became data, read when it is used.

But a task is never a point. “Pay this supplier invoice in euros and let them know” is a path: approve the invoice, convert the amount, pay, post the ledger entry, send a message. That path crosses three or four servers. Somebody has to draw it.

Today, the agent draws it. The model reads the tool descriptions, reasons about the task and chooses each call. The path exists, but only in one place and for one moment: the context window of one run. When the run ends, the path is gone. The next agent facing the same task draws it again from scratch.

2. A dictionary without a grammar

A better image than points is language. MCP gives us a dictionary. Each entry defines one word clearly and in a standard form. What a dictionary does not tell you is how to build a sentence: which words go together, in what order, which ones can stand in for each other, which combinations are wrong. That is the job of a grammar.

So what is missing from MCP is not an algorithm. It is a kind of object. MCP has first-class tools, resources and prompts. It has no first-class relation between them. As long as relations are not part of the vocabulary, nobody can publish one, share one, version one or check one. Every agent keeps its own private grammar, and nobody else can read it.

Resemblance is not complementarity

The current answer to large catalogues is search. Tools stay out of the context and are found by matching the request against their descriptions (Anthropic 2025c; Gan and Sun 2025), sometimes server first, then tool (Fei et al. 2025). This finds tools that resemble the request. A task needs tools that complete each other.

“Pay this supplier invoice in euros” resembles the invoice tools. It does not resemble the ledger or the mail server, yet the task needs both. The relation between paying an invoice and posting a ledger entry is not in either description. It is in the use.

Recommender systems learned this long ago. Shops distinguish products that substitute for each other (two similar cameras) from products that complement each other (a camera and a memory card), and the two kinds of relation have to be learned differently (McAuley et al. 2015). The oldest working answer, “customers who bought this also bought that”, does not look at descriptions at all: it counts what is used together (Linden et al. 2003). Tool retrieval has rediscovered the point. COLT showed in 2024 that matching a request to tool descriptions returns redundant tools and misses the complementary ones a multi-part request needs, and proposed retrieval aimed at the complete set (Qu et al. 2024). Tool2Vec embeds each tool from the requests that actually used it rather than from its description, and recalls far better (Moon et al. 2024). Both learn from use; both keep what they learn inside one system. Tool search in production is still mostly stuck at the first kind of relation. A grammar is how we write down the second, in a form others can read.

3. Why it matters now

With a few dozen tools, the agent can read every definition and draw the path itself. Nothing needs to be stored, nothing goes stale. The cost appears when catalogues grow, and two things grow with them.

The first is the cost of looking. MCP-Zero counts about 4,600 tokens for the 26 tools of the GitHub server alone (Fei et al. 2025). A thousand tools fill a large context window before the task has begun.

The second is the space of compositions. With N tools there are N^k ordered chains of k of them. The chains anyone actually uses are a vanishing fraction of that space. The useful structure is small, roughly linear in N, but nobody writes it down. So every run looks for it again inside a space that grows with the fourth power.

This is no longer a projection. LiveMCPBench gave agents 70 MCP servers and 527 tools across 95 everyday tasks. The best model completed 79% of them, most models only 30% to 50%, and the authors identify finding the right tool as the dominant bottleneck (Mo et al. 2025). MCP-Bench connected 20 models to 250 tools on 28 live servers, in tasks that chain tools within and across servers, and found persistent difficulty with long-horizon planning, with weaker models degrading most on multi-server tasks (Wang et al. 2025). Both point at the same gap: knowing which tools go together.

The field has noticed, and the answers so far tell the story:

  • Groups. A proposal for MCP, SEP-1300, lets servers put tools into groups and tags, so a client can load one functional area at a time (Model Context Protocol 2025e). Groups are sets: they say which tools belong together, not how they combine. They are the right first step, and relations are the natural next one.
  • Prompts. MCP servers can already publish prompts, templated workflows written in prose (Model Context Protocol 2025c). A prompt is a sentence, not a grammar: it lives on one server, is chosen by the user and cannot be checked or combined with prompts from other servers.
  • Skills. Agent Skills package instructions, scripts and tool use for one job (Anthropic 2025b). Each skill contains a small grammar, written by hand, for one bundle.
  • Research systems walk graphs of tool transitions learned from past runs (Liu et al. 2024), follow dependency edges after a first search (Lumer et al. 2025), or learn tool representations from use (Qu et al. 2024; Moon et al. 2024), each inside one system. Benchmarks such as TaskBench already describe tasks as tool graphs, with tools as nodes and dependencies as edges (Shen et al. 2024): the research community models the grammar, but only to evaluate agents, not to publish it.

Each of these holds a piece of the grammar. None can be read by anyone else, because the protocol has nowhere to put a relation. The protocol itself has moved fast: tool annotations arrived in March 2025 (Model Context Protocol 2025b), output schemas in June (Model Context Protocol 2025c), and the November 2025 revision added icons, guidance on tool names and long-running tasks (Model Context Protocol 2025d). None of them adds relations between tools. The 2026 roadmap focuses on transport, agent communication, governance and enterprise readiness (Model Context Protocol 2026); as far as I can tell, typed relations are not on it.

4. This was tried before

Describing how operations connect is an old idea, and it is worth asking why it did not take hold.

OpenAPI links. Since version 3.0, an OpenAPI description can say that a value returned by one operation is the input of another, with the exact field mapping: the id in the response of createUser becomes the userId parameter of getUser (OpenAPI Initiative 2017). That is precisely the feeds relation of this essay, standardised in 2017. It exists, it works, and few people use it. REST APIs got links between operations; MCP tools never did.

Arazzo and agents.json. In 2024 the OpenAPI Initiative published Arazzo, a specification for describing multi-step workflows across APIs: which operations to call, in which order, and how outputs become inputs (OpenAPI Initiative 2024). In 2025, agents.json built on OpenAPI to give AI agents “flows” and “links” for the same purpose (Wildcard AI 2025). These are the closest relatives of this essay, and they show that the need is real. But they write down sentences, complete workflows chosen in advance. They do not give a grammar from which an agent can build a sentence nobody wrote, and they say nothing about what was observed in use or forbidden by policy. A grammar and a set of sentences are complementary: a known workflow is a sentence the grammar allows, and a good workflow format is a natural way to publish one.

Semantic web services. In the early 2000s, OWL-S and WSMO described web services with inputs, outputs, preconditions and effects, so that software agents could find and compose them automatically (Martin et al. 2004; Bruijn et al. 2005). “Requires” is a precondition; “feeds” is an output matched to an input. The vision was close to this essay’s. It stalled, for two reasons: writing formal descriptions in shared ontologies cost far more than anyone would pay, and the reasoners that consumed them broke on anything imprecise.

What changed is the reader, the same argument I made in The Interface Is Data for self-describing APIs. A language model does not need a perfect ontology. It can use a relation that is partial, approximate or written in plain words, and weigh it against everything else it knows. And one of the four sources below, observed use, needs no author at all. A grammar that was too expensive to write precisely for a strict reader becomes cheap enough to write roughly for a tolerant one.

5. Where the grammar comes from

If relations are to become data, the first questions are where they come from and who keeps them. I see four sources. They differ in cost, in trust, and in who owns them.

5.1 Computed from types

Since its June 2025 revision, MCP lets a tool declare an outputSchema, the shape of what it returns, next to its inputSchema (Model Context Protocol 2025c). That is enough to derive some edges with no one declaring anything. If one tool returns a payment_id and another requires one, the first probably feeds the second.

Computed edges are cheap, and anyone can derive them: the client, a gateway, a catalogue. They are also checkable, since a test can confirm that the output of one tool still fits the input of the other. Their limits are real. They find data flow, not intent; field names are noisy; and output schemas are optional in MCP. I have not measured how many public servers declare them today. If few do, this source is a promise rather than a resource, and the first practical step is simply to publish output schemas.

5.2 Declared by authors

Some relations only the author knows. That paying requires an approval first. That schedule_payment is an alternative to paying now. That a tool is usually followed by a notification. These are short statements, and MCP already lets a tool carry extra metadata where they could live. They belong to the server, and travel with its tools.

Declared edges carry intent, which no other source has. They are also partial, since an author sees only their own side of a workflow, and they can be self-serving: every server has a reason to declare edges toward itself.

5.3 Observed in use

Every agent already draws the grammar on every run. If clients kept the paths they walked, they could count which tools are used together and turn the counts into weights. This is the truest source: it shows what actually happens, including partners nobody thought to declare.

It is also the most sensitive. What an organisation’s agents do is private, so observed edges belong to the client and stay inside the organisation by default, shared only as aggregated weights if at all. Counting them the same way everywhere needs a common trace format. That could be part of MCP, or a convention in an existing tracing standard such as OpenTelemetry; what matters is that it is shared.

5.4 Imposed by the organisation

A grammar does not only say what goes together. It can also say what must not. Simon Willison’s “lethal trifecta” names a dangerous combination: an agent that reads private data, is exposed to untrusted content and can communicate externally (Willison 2025). Each tool may be safe on its own; the danger is in the combination. An organisation should be able to write that down as a rule, excludes, and have it enforced.

This rule does not belong to any server. A vendor publishes its tools; it does not decide what your company forbids. Policy edges belong to the client or the gateway that sits between agents and servers, and they override every other source.

6. A grammar at two levels

A grammar in the linguistic sense does not link specific words. It works on kinds of words: a verb takes an object, an adjective goes before a noun. Specific words that habitually appear together, “strong coffee” rather than “powerful coffee”, are called collocations, and they are learned by use. A tool grammar needs both levels.

Table 1. The two levels of a tool grammar, by analogy with language.
In language For tools Example
parts of speech roles: what kind of thing a tool does approves, pays, converts, notifies, reads private data
grammar rules relations between roles anything that pays requires something that approves
collocations relations between named tools, with weights this payment tool is usually used with that converter (0.71)
a sentence the path of one task approve, convert, pay, post, notify

The two levels fail in opposite ways, which is why both are needed. Collocations are precise for the work an organisation already does, and they say nothing about a tool that was installed yesterday or a workflow nobody has run. Rules over roles carry over to new tools immediately, but they are coarse: they say a payment needs an approval, not which one. A new tool that declares its roles fits into the grammar on the day it appears; use then sharpens the rules into collocations.

MCP already has the beginning of a role system. Tool annotations say whether a tool is read-only, destructive, idempotent or reaches the open world (Model Context Protocol 2025c). These are parts of speech in all but name. The lethal-trifecta rule, for instance, can already be written partly over them: a tool with an open-world hint should not run in the same task as one that reads private data. What is missing is a small shared list of roles beyond those hints, and a way to write rules over them.

6.1 A starting vocabulary

Five relations are a reasonable start. They will not cover everything (conditions such as “if this fails, use the alternative”, or order beyond requires, would come next), but they cover a lot.

Table 2. A proposed starting vocabulary of relations, usable between roles or between named tools.
Relation Meaning Typical source
requires must have run before declared
feeds its output is the other’s input computed
used with often in the same task observed
alternative can replace the other declared
excludes must not run in the same task policy

Each relation can point to a role or to a named tool, and each edge says where it came from so that a reader can weigh it.

6.2 What the protocol needs, and what it does not

What MCP itself would need is small:

  1. A place for relations. Today a convention in _meta, which MCP already allows on tools (Model Context Protocol 2025c); later a field of its own, if the convention proves useful. Tool groups, if adopted, are a natural home for rules that hold inside a group.
  2. A shared vocabulary. A short list of roles, and the five relations above.
  3. Stable names. See below.
  4. A shared way to count use. Whether in MCP or in an existing tracing convention.

The route for such a change exists: MCP evolves through public enhancement proposals, and since December 2025 the protocol is stewarded by the Agentic AI Foundation rather than by a single company (Anthropic 2025a). A convention in _meta can be tried first, by a few servers and clients, and proposed once it has shown it is useful.

What it should not include is just as important: any particular way of using the relations. How a client ranks tools, walks the graph or loads a neighbourhood is the client’s business. MCP should carry the grammar, not decide how to read it.

6.3 Edges are local; names are not

Could all of this live in a central registry instead? For composition, I think not. Early web directories sorted pages into folders and were overtaken by search that read the links pages carried themselves (Brin and Page 1998). Links worked because each page published its own and nobody had to hold the map (Fielding 2000). MCP today is a web of pages without links, and each tool should carry its own.

But the web analogy cuts both ways. Links needed no central map, yet they did need a central naming system: a URL is only useful because DNS says what a domain is. The same holds here. An edge to “the convert tool on the fx-rates server” is only meaningful if fx-rates names the same server for everyone, and MCP tool names are unique only within one server; the November 2025 revision added guidance on how to name tools, not a way to name them across servers (Model Context Protocol 2025d). Rules over roles avoid the problem, which is one more reason to prefer them. Edges to named tools across servers need a registry that gives servers stable identities, and the MCP Registry is the obvious candidate (Model Context Protocol 2025a). So the honest position is: relations are local and decentralised; names are not. That is a modest layer, for identity, not a layer that holds the grammar.

7. Borrowing from neural networks

My first idea for this essay was to treat the tool ecosystem as a neural network: tools as neurons, edges as synapses, and a graph neural network (Gilmer et al. 2017) deciding which tools fire for each task. I built one in a small simulation. It worked, but no better than a plain walk along the edges, and it struggled on workflows it had never seen, exactly where rules over roles help. What survived was not the network. It was the principles.

Large neural networks work because they are built on a handful of ideas. Each of them becomes a design rule for a tool grammar:

Table 3. Five principles borrowed from neural networks, and what each means for a tool grammar.
Concept In a neural network As a design rule for tools
Locality a unit only receives messages from its neighbours a tool knows only its neighbours; nobody holds the global map
Sparse activation few units fire for any input (Olshausen and Field 2004; Shazeer et al. 2017) a task loads one neighbourhood, never the catalogue
Plasticity connections that fire together strengthen (Hebb 1949) observed edges strengthen with use and fade without it
Modularity modules are assembled differently for each question (Andreas et al. 2016) clusters that work together become units, across servers
Gating the input decides which paths open the task decides which edges count: a notify edge matters for a payment, not for a report

Sparse activation is the one that pays most directly. Instead of searching a catalogue of thousands, an agent finds one good starting tool by meaning, then loads its neighbourhood: a handful of tools that the grammar says belong with it. Search finds the door; the grammar shows the rooms behind it.

Modularity is where my first intuition about entanglement belongs. Some clusters of tools cannot be understood one at a time: what happens in invoicing tells you a lot about what will happen in currency and mail, whatever the description of any single tool says. Physicists call systems that cannot be described part by part entangled (Horodecki et al. 2009). Nothing quantum happens in a tool catalogue, and the useful mathematics here is ordinary statistics. But the intuition holds. The unit of design is no longer the single tool. It is the group of tools that work together, which can be found from the edges themselves (Newman 2006). Groups and skills are such units, drawn by hand. A grammar lets them emerge from use and cross server boundaries.

8. Who reads the grammar

The strongest argument for relations as data is the one I made for tool descriptions: once something is data, many readers can use it, and most of them need no AI.

  • The language model is the main reader. It does not need a smarter ranking function; it needs the right few tools in its context. Given a tool and its neighbourhood, a model reasons about them far better than it can about a list of thousands. It is also the reader that tolerates an imperfect grammar, which is what makes this attempt different from the last one.
  • A workflow engine can run a path the grammar already knows, with no model at all.
  • A policy gateway can block any call that would complete an excluded pair in the same task.
  • Contract tests can check, on every release, that each feeds edge still type-checks.
  • A catalogue can show people how tools combine, not just what each one does.
  • A small learned router can come later, once the same routing decisions repeat often enough to be worth compiling, as I argued in Fast AI and The Junior Colleague. It is an optimisation, not the paradigm.

9. Objections

“Keep MCP small. Composition belongs to clients and skills.” This is the strongest objection. My answer is that skills and groups prove the need: each skill contains a hand-made grammar, and each group is a set of tools someone decided belong together. But skills are written by one author and live inside one vendor, and groups say nothing about order or data flow. A short list of roles and five relations cost the protocol little. Leaving them out guarantees that every client invents its own version, and none can read the others’.

“This is the semantic web again.” In ambition, yes. In economics, no. The semantic web needed precise descriptions written by people for strict machines. A tool grammar can start from what is free (schemas and observed use), add a little that authors know, and be read by a model that copes with gaps.

“Retrieval trained on use already solves this, with no protocol change.” COLT and Tool2Vec show that learning from use beats matching descriptions (Qu et al. 2024; Moon et al. 2024), and I agree. But what they learn stays inside one retriever: it cannot be shared between clients, checked against schemas, overridden by policy or read by a workflow engine. A grammar does not replace learned retrieval. It gives learned retrieval somewhere to write what it found, and something to start from on the first day.

“Arazzo already does this.” Arazzo describes fixed workflows over OpenAPI operations. MCP tools are not OpenAPI operations, and a fixed workflow does not help an agent build a new one. Arazzo is a good format for the sentences; a grammar is what makes new sentences possible.

“The model can work out complementarity by itself.” Often it can. A model knows that paying in euros may need a currency conversion. It does not know that your company requires approve_invoice before any payment, or that your ledger tool must follow your payment tool. Local conventions are exactly what a grammar records. It also saves the tokens and the time of working them out again on every run.

“Declared edges will be gamed.” Some will. That is why every edge names its source. A client can trust computed and policy edges, discount declared ones from servers it does not know, and let observed weights correct both. A declared edge that nobody ever walks fades.

“Observed edges leak what we do.” They should stay with the client by default. The protocol only needs a common way to count; sharing aggregated weights is a choice, not a requirement.

“Structure will fence the model in.” The strength of the flat catalogue is that a model may draw a path nobody foresaw. A grammar should decide what to show first, not what is allowed, except for the excludes rules an organisation imposes on purpose.

“Edges will go stale.” Tools change. Edges versioned with their tools, computed edges re-checked on every release, and observed weights that decay without use limit the damage. The flat catalogue never goes stale, but it never learns either.

10. What would prove me wrong

  • If context windows and tool search grow faster than catalogues, so that an agent can always read every relevant description, then the grammar adds maintenance and little else.
  • If real tool descriptions carry the complementary signal, so that “pay an invoice” does in practice sit close to “post a ledger entry” in embedding space, then search by meaning would do most of the work. This can be measured on real servers and real traces.
  • If computed edges turn out to be rare or noisy, the cheapest source disappears. This is easy to check: count how many public MCP servers declare output schemas, derive feeds edges from them, and see how many a person would accept.
  • If OpenAPI links stay unused for the same reasons in MCP, the problem is incentives, not the absence of a field, and a field alone will not help.
  • If retrieval trained on use, such as Tool2Vec or COLT, closes the gap that benchmarks like LiveMCPBench measure, without any shared relations, then the grammar’s value shrinks to policy and auditing.
  • If groups, skills and explicit workflows (Arazzo-style) cover the frequent work, the gain from a shared grammar would shrink to the long tail. I suspect the tail is where much of the value is, but that is a hypothesis.

11. Conclusion

MCP got the hardest part right. It turned every tool into a definition that any caller can read. What it left out, for good reasons at first, is how the definitions combine. Today every agent rebuilds that knowledge in its context window and throws it away at the end of the run.

What is missing is not a new central layer and not a trained network. It is a small grammar at two levels: rules about kinds of tools, which hold for tools nobody has used yet, and habits of specific tools, learned from use. Relations can be computed from schemas, declared by servers, observed by clients and imposed by the organisation, and each one should say where it came from. The idea is old; OpenAPI, Arazzo and the semantic web tried parts of it. What is new is a reader that can use a grammar that is cheap, partial and imperfect. The ideas that make neural networks scale tell us how that grammar should behave, and we can borrow them without building a network.

A dictionary lets you look words up. A grammar lets you say something. MCP has the first. The second is what large ecosystems of tools now need.
